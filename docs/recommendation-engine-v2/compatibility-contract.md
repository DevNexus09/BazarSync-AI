# Recommendation engine compatibility contract

## API and consumers

Paths below use the default `/api/v1` prefix. The existing authenticated routes and [general recommendation schemas](../../backend/app/schemas/recommendation.py) remain the public interface. The dashboard's optional seller filter passes through the authenticated seller-scope check before the repository query.

| Method and path | Current contract |
| --- | --- |
| `POST /recommendations/generate/{product_id}` | 202 with `success`, `status: "processing"`, `product_id` and `task_id`. Queuing follows seller-scoped preflight. Preserve the task name and its existing positional string arguments while old messages are in flight. |
| `GET /recommendations/latest/{product_id}` | 200 with `success`, `product_id`, `recommendation`, `analytics`, and UTC-compatible `created_at`. Latest selection sorts by `created_at DESC, id DESC` after ownership verification. |
| `GET /dashboard/recommendations` | Existing filtered, sorted and paginated dashboard view uses the general history, including its stored analytics. Dashboard opportunity and summary consumers also use recommendation data. |
| `POST/GET /products/{product_id}/pricing/recommendations`, `GET …/pricing/recommendations/latest` | Specialized pricing generation, history and latest read. `GET /pricing/recommendations/{id}` and its `acknowledge` and `dismiss` POST actions retain their existing lifecycle contracts. |
| `GET /inventory-intelligence/products/{product_id}`, `GET /inventory-intelligence/reorder-list` | Existing product and list views expose reorder evidence. Preserve workflow enqueue routes and the `acknowledge`, `mark-ordered`, and `dismiss` POST actions under `/reorder-recommendations/{id}`. |
| `GET /products/{product_id}/dead-stock/recommendation` and `GET /products/{product_id}/dead-stock/recommendations` | Latest and history views for recovery. Preserve the `acknowledge` and `dismiss` POST actions under `/dead-stock/recommendations/{id}`. |

The general response preserves action `LOWER|RAISE|HOLD|REORDER`, confidence `LOW|MEDIUM|HIGH`, Bangla `reasoning_bn`, and numeric nonnegative `revenue_opportunity`. Analytics has nullable `competitor_median_price`, `price_gap_percent` and `competitors_oos`, required 0–1 `stock_risk_score` and `pricing_pressure_score`, and required nonnegative `estimated_days_of_stock_left`. Preserve these names, types and nullability. An additive evidence/status field or versioned surface can express unavailable data alongside fields that the legacy contract requires to be numeric. Keep synthetic legacy defaults out of new evidence and forecasts.

Task 19 adds optional `dashboard_evidence` to general recommendation results, including nested durable-job results, behind `RECOMMENDATION_DASHBOARD_EVIDENCE_ENABLED`. The field is omitted when disabled or unsupported by the saved record. It exposes a typed seller-visible summary while retaining the internal decision snapshot. Frontend sections require `VITE_RECOMMENDATION_DASHBOARD_V2`. [Summary rules and rollback](task-19-recommendation-dashboard.md)

Known service failures return `{success: false, detail, error_code}`. These include 404 `product_not_found`, `competitor_data_missing`, and `recommendation_not_found`, and 400 `analytics_failure`. JWT failures and invalid UUID path parameters use FastAPI's auth and validation responses. Keep the same foreign-product behavior as for an absent product. Preserve event names and payloads consumed by the dashboard and seller-room access controls. Any additive per-run status lookup must verify seller and product scope regardless of whether a task ID is known.

## Data model and migration constraints

The table describes code and migration definitions. The audit did not inspect the schema or data of any existing seller database.

| Records | Constraints and implications |
| --- | --- |
| [Recommendation](../../backend/app/models/recommendation.py) | PostgreSQL UUID primary key and product FK with cascade. Seller scope follows product ownership. Native action/confidence enums, non-null reasoning, `Numeric(14,2)` revenue opportunity, and non-null JSONB context. Nullable `Numeric(12,2)` suggested price bounds have a range-order check. A product/created-time index supports latest reads. No per-task or per-decision unique key exists. Preserve IDs, timestamps, legacy flat snapshots and nested snapshots, including the analytics keys dashboard readers extract. |
| [ScrapeRun](../../backend/app/models/scrape_run.py), [Competitor](../../backend/app/models/competitor.py), [CompetitorSnapshot](../../backend/app/models/competitor_snapshot.py) and [PriceHistory](../../backend/app/models/price_history.py) | Scrape runs carry seller and product scope. Competitors link to product and run. Join scoped inputs, retain source timestamps, and allow unavailable prices and stock status. Snapshots are unique by scrape run/competitor/product and use explicit `IN_STOCK`, `OUT_OF_STOCK` and `UNKNOWN` states. Competitor price history links to the competitor and uses `observed_at`. Neither competitor prices nor marketplace sold counts establish seller transaction price or demand. |
| [SalesRecord](../../backend/app/models/sales_record.py) and [SalesDataCoverage](../../backend/app/models/sales_data_coverage.py) | Sales link to seller and product. Zero sales and incomplete observation coverage must remain distinguishable. |
| [InventoryHistory](../../backend/app/models/inventory_history.py), [InventoryStockIn](../../backend/app/models/inventory_stock_in.py), [SalesVelocity](../../backend/app/models/sales_velocity.py) and [StockoutPrediction](../../backend/app/models/stockout_prediction.py) | Inventory history is unique by seller/product/snapshot date. | [ProductPriceHistory](../../backend/app/models/product_price_history.py), [ProductMarketplaceListing](../../backend/app/models/product.py) and [PricingPolicy](../../backend/app/models/pricing_policy.py) | Seller price changes are timestamped and scoped by seller/product and optionally listing. | [DynamicPricingRecommendation](../../backend/app/models/dynamic_pricing_recommendation.py) | Seller/product/pricing snapshot/objective/formula uniqueness, plus a partial unique index for OPEN rows keyed by seller/product/objective/formula version. | [ReorderRecommendation](../../backend/app/models/reorder_recommendation.py) and [DeadStockRecoveryRecommendation](../../backend/app/models/dead_stock_recovery_recommendation.py) | Reorder is unique by product, as-of date and calculation version. Recovery is unique by assessment and calculation version. Both carry seller/product scope, evidence, bounded confidence and status. Keep the associated assessment/prediction relationships and status transitions. |
| [RagIndexOutbox](../../backend/app/models/rag_index_outbox.py) and [RagMemory](../../backend/app/models/rag_memory.py) | Indexing has its own dedupe key and retry lifecycle. A newly inserted recommendation ID creates a distinct source. Preserve seller-scoped upserts, deletion handling and retrieval filters. |

## Decision, evidence and rollout

- Keep seller ownership checks at API and worker boundaries and use seller-scoped joins, caches, input snapshots, status lookups and retrieval. Reuse the specialized services as owners of their decisions.
- Use Decimal for price, margin and fee calculations. Pass the exact candidate, seller, product and marketplace to MarginGuard immediately before publishing an actionable price. Missing cost or fee evidence must block a price change. Recommendation creation and lifecycle updates are advisory only.
- Carry observation time, provenance, completeness, method, versions, uncertainty and rejection reasons. Never fill missing demand, revenue, profit or competitor observations with made-up values. Explanations may summarize validated facts and uncertainty. The LLM cannot change actions, confidence, prices or financial outputs.
- Keep major changes behind explicit default-off flags with consistent web/worker settings and a disable path. Keep training offline, compare against deterministic baselines out of time, and require data coverage and safety metrics before seller-facing rollout.
- Use bounded retries and timeouts. Put durable recommendation and outbox writes in a transaction and use a seller-scoped idempotency key for new work. Use the persisted result to correlate completion and separate successful persistence from post-commit delivery failures.
