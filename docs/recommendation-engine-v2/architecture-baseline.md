# Recommendation engine architecture baseline

Inspected 14 November 2026 on `develop` at `6f796ea`, including the local working tree. “General recommendation” refers to the recommendation screen and the `recommendations` table. Dynamic pricing, reorder and dead-stock recovery maintain their own records and workflows.

The flow below describes the audit baseline. See [Task 1](task-1-competitor-evidence.md) for the opt-in freshness path and current deployment settings.

## General recommendation request and delivery

1. [API routes](../../backend/app/api/v1/recommendations.py) are mounted by [the v1 router](../../backend/app/api/router.py). [Seller authentication](../../backend/app/dependencies/auth.py) validates the bearer JWT, resolves its seller subject and checks the token's auth version. The service queries the product by both ID and seller ID. Cross-seller and absent products use the same product-not-found result.
2. Generation preflight loads competitors from the latest completed scrape for that seller and product, ordered by finish time then creation time. It accepts both `COMPLETED` and `completed`, selects competitor rows by product and scrape-run IDs, orders by similarity, drops null prices, runs analytics and validates prompt context. Missing run or priced rows fail preflight. The async route performs this work with a synchronous session before publishing a Celery job and returning 202.
3. [The worker](../../backend/app/tasks/recommendation_tasks.py) receives string IDs under `analytics.generate_ai_recommendation`, validates UUIDs and seller/product alignment, opens its own session and reruns the data loads and computations. Older task callers may omit seller ID, in which case the task resolves the product owner. Invalid scope and known precondition failures are ignored. AI, persistence and SQLAlchemy errors are configured for up to two retries with backoff and jitter. [Celery](../../backend/app/core/celery_app.py) uses Redis for broker and results, late acknowledgments, worker-loss rejection, a prefetch multiplier of one and one-hour result expiry.
4. [PricingEngine](../../backend/app/analytics/pricing_engine.py) computes observed price statistics, availability, price gaps and heuristic scores. Its rule order is `REORDER`, `LOWER`, `RAISE`, then `HOLD`. [StockEngine](../../backend/app/analytics/stock_engine.py) recomputes stock and availability scores using [shared metrics](../../backend/app/analytics/metrics.py). The service merges these into the pricing output. General stock cover uses a synthetic base velocity of one unit per day adjusted by price gap and availability, without seller sales history.
5. [RecommendationService](../../backend/app/services/recommendation_service.py) validates the candidate with [MarginGuard](../../backend/app/services/margin_guard.py). `LOWER` starts from the competitor median, while `RAISE` currently checks the current selling price. A disallowed price action becomes `HOLD` with reduced confidence. MarginGuard uses the seller/product pricing policy, recorded fees, unit cost, profit and margin floors, price bounds, change limits and price increment rules. The general flow uses its default Daraz Bangladesh marketplace.
6. [RecommendationContextBuilder](../../backend/app/analytics/recommendation_builder.py) normalizes inputs for [Groq prompts](../../backend/app/ai/prompts.py) and [AI schemas](../../backend/app/ai/schemas.py). [RecommendationGenerator](../../backend/app/ai/recommendation_generator.py) validates strict JSON, a Bangla-character check, exact action and mapped confidence, and zero revenue opportunity. The generator therefore depends on Groq for explanation even when the decision is already computable. Schema validation does not establish factual support for claims in free text.
7. Before persistence the service checks MarginGuard again. A new `Recommendation` and its seller-scoped RAG upsert outbox entry are flushed and committed together. JSONB stores `context`, `analytics` and final `margin_guard` evidence. New general rows have null suggested-price bounds and zero revenue opportunity. [RAG tasks](../../backend/app/tasks/rag_memory_tasks.py) claim leased outbox batches and reindex or soft-delete the seller's source. Failed entries back off or dead-letter. Reconciliation can repair missed records, and pending chunks are embedded separately. [The source registry](../../backend/app/services/rag_memory_source_registry.py) registers recommendation content for seller-scoped indexing. RAG search does not feed the general decision.
8. After commit the service attempts `recommendation_created`, urgency and dashboard summary events to the seller room through [RealtimeService](../../backend/app/services/realtime/realtime_service.py), and a market opportunity event only for positive opportunity. The stock-risk helper currently logs above its threshold. [Socket initialization](../../backend/app/websocket/socket_manager.py) occurs in the FastAPI app factory. A standalone worker has no demonstrated emitter initialization and the service explicitly skips emission when unavailable.
9. The [recommendation page](../../frontend/src/pages/recommendations/RecommendationDashboardPage.tsx) uses an [Axios adapter](../../frontend/src/pages/recommendations/services/recommendationApi.ts) and [React Query hook](../../frontend/src/pages/recommendations/hooks/useRecommendation.ts). It treats latest-GET 404 as empty and polls every five seconds once queued, stopping when a row has `created_at` at or after the browser's queue timestamp. It keeps the task ID but never checks its status. Socket connections authenticate and authorize room subscriptions. The server can use its Redis Socket.IO manager when a broker URL is configured. The separate [dashboard hook](../../frontend/src/hooks/useLiveDashboard.ts) handles Socket.IO recommendation events for dashboard state and the live feed.

## Dependencies and configuration

- Backend [requirements.txt](../../backend/requirements.txt) includes FastAPI/Pydantic, SQLAlchemy/Alembic and psycopg2/asyncpg, Celery/Redis, Groq/Tenacity, Python Socket.IO, NumPy/pandas and existing ML packages such as scikit-learn, SciPy, SentenceTransformers and torch. RAG needs a pgvector-capable PostgreSQL instance and local BGE embeddings by default. Playwright/Daraz supplies competitor inputs.
- [Dockerfile](../../Dockerfile) uses a floating Playwright Python base image. [Compose](../../docker-compose.yml) defines web, worker and Redis services. PostgreSQL and beat require separate provisioning. Local Python 3.14 validation does not establish the image's interpreter or wheel compatibility.
- `GROQ_API_KEY`, `GROQ_MODEL`, `GROQ_TIMEOUT_SECONDS` (30 seconds by default) and `GROQ_MAX_RETRIES` (3) configure the client. The Groq client, generator and worker have separate retry layers. `BAZARSYNC_STOCK_RISK_EVENT_THRESHOLD` defaults to 0.7. There is no general recommendation v2 flag.
- `SCRAPER_SCHEDULE_ENABLED`, `INVENTORY_INTELLIGENCE_SCHEDULE_ENABLED`, `DEAD_STOCK_WORKFLOW_SCHEDULE_ENABLED`, `DEAD_STOCK_ALERTS_ENABLED` and `RAG_MEMORY_SCHEDULE_ENABLED` default off. `RAG_ENABLED` defaults off and gates RAG API access independently of scheduled indexing. Outbox creation in general recommendation persistence is unconditional. `DYNAMIC_PRICING_*` tunes formula, thresholds and expiry. `DEMAND_RESPONSE_*` controls eligibility and the labeled heuristic fallback.
- Frontend uses React, React Router, Axios, TanStack Query and Socket.IO client. `VITE_API_BASE_URL` points at the backend. Keep Groq, broker and database credentials server-side.
- Related documentation includes [competitor intelligence](../phase5.md), [inventory intelligence](../phase6.md), [pricing policy](../phase7.md) and [Daraz operations](../daraz-operations.md). Consult current models and services when phase notes describe earlier schema assumptions.
