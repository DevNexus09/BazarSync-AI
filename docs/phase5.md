# Phase 5 Competitor Intelligence

## Architecture

Phase 5 turns completed scrape runs into durable analysis records and dashboard updates.

Workflow:

1. Scraper stores competitor rows for a seller-owned product.
2. `scrape_runs` is committed as `COMPLETED`.
3. `competitor_snapshots` stores immutable competitor observations.
4. `phase5.run_analysis_workflow` generates events.
5. Rankings are calculated for the completed run.
6. Market opportunities are generated from eligible trigger events.
7. Dashboard update envelopes are published through the existing Socket.IO emitter.
8. The frontend validates Phase 5 Socket.IO envelopes and invalidates TanStack Query keys.
9. Widgets refetch APIs; database state remains the source of truth.

Failed and partial runs do not generate events, rankings, or opportunities.

## Database Schema

### `scrape_runs`

Phase 5 adds:

- `seller_id`
- `marketplace`
- `run_key`
- uppercase lifecycle statuses: `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `PARTIAL`
- `completed_at`
- `failed_at`
- `discovered_competitor_count`
- `snapshot_count`
- `failure_code`
- `updated_at`

Unique constraint:

- `(seller_id, product_id, marketplace, run_key)`

### `competitor_snapshots`

Immutable observations for one competitor in one scrape run.

Important columns:

- `scrape_run_id`
- `competitor_id`
- `product_id`
- `price NUMERIC(12,2)`
- `rating NUMERIC(3,2)`
- `review_count`
- `stock_status`
- `captured_at`
- `content_hash`

Constraints:

- non-negative price
- rating between 0 and 5
- non-negative review count
- stock status is `IN_STOCK`, `OUT_OF_STOCK`, or `UNKNOWN`
- unique `(scrape_run_id, competitor_id, product_id)`

### `competitor_events`

Immutable business events generated by comparing completed scrape runs.

Event type enum:

- `PRICE_DROP`
- `PRICE_RISE`
- `OUT_OF_STOCK`
- `BACK_IN_STOCK`
- `NEW_COMPETITOR`
- `COMPETITOR_REMOVED`

Severity enum:

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

Important constraints and indexes:

- unique `dedupe_key`
- `(product_id, detected_at)`
- `(competitor_id, detected_at)`
- `(event_type, detected_at)`
- `(scrape_run_id)`
- `(seller_id, detected_at)`

### `competitor_rankings`

Historical ranking records by scrape run and formula version.

Unique constraint:

- `(scrape_run_id, competitor_id, formula_version)`

Indexes:

- `(product_id, calculated_at)`
- `(scrape_run_id, market_rank)`
- `(competitor_id, calculated_at)`
- `(seller_id, calculated_at)`

### `market_opportunities`

Opportunity records generated from eligible event triggers.

Unique constraint:

- `trigger_event_id`

Indexes:

- `(seller_id, status, detected_at)`
- `(product_id, detected_at)`
- `(opportunity_level, detected_at)`
- `(scrape_run_id)`

## Event Definitions

`PRICE_DROP` is generated when previous and current snapshots both have valid prices, the current price is lower, and the change passes the configured absolute or percentage threshold.

`PRICE_RISE` uses the inverse price logic.

`OUT_OF_STOCK` is generated only when previous status is `IN_STOCK` and current status is `OUT_OF_STOCK`.

`BACK_IN_STOCK` is generated only when previous status is `OUT_OF_STOCK` and current status is `IN_STOCK`.

`NEW_COMPETITOR` is generated when a competitor exists in the latest completed run and did not exist in the previous completed run. The first completed run is a baseline and does not emit new-competitor events.

`COMPETITOR_REMOVED` is generated only after the competitor is absent from the configured number of consecutive completed runs. The default is two completed runs.

## Event Thresholds

Environment variables:

- `COMPETITOR_EVENT_MIN_PRICE_CHANGE_ABSOLUTE`, default `1.0`
- `COMPETITOR_EVENT_MIN_PRICE_CHANGE_PERCENT`, default `1.0`
- `COMPETITOR_REMOVAL_CONSECUTIVE_RUN_THRESHOLD`, default `2`

The price event passes if either the absolute or percentage threshold is met.

## Ranking Formula

Formula version defaults to `v1`.

Scores are normalized to 0-100:

- price score: lower valid prices score higher within the same completed run
- rating score: `rating / 5 * 100`
- review score: logarithmic normalization against max review count in the run
- availability score: `IN_STOCK=100`, `UNKNOWN=50`, `OUT_OF_STOCK=0`

Default weights:

- price: 35
- rating: 30
- review: 20
- availability: 15

Weights must total 100.

Environment variables:

- `COMPETITOR_RANKING_PRICE_WEIGHT`
- `COMPETITOR_RANKING_RATING_WEIGHT`
- `COMPETITOR_RANKING_REVIEW_WEIGHT`
- `COMPETITOR_RANKING_AVAILABILITY_WEIGHT`
- `COMPETITOR_RANKING_FORMULA_VERSION`

Changing weights should use a new formula version so historical rankings are not silently rewritten.

## Opportunity Formula

Eligible trigger event types:

- `OUT_OF_STOCK`
- `PRICE_RISE`
- `COMPETITOR_REMOVED`

Opportunity score components:

- trigger impact
- competitor strength
- stock readiness
- price readiness
- data confidence

Default weights:

- trigger impact: 30
- competitor strength: 25
- stock readiness: 20
- price readiness: 15
- data confidence: 10

Default thresholds:

- high: 75
- medium: 45

Environment variables:

- `MARKET_OPPORTUNITY_TRIGGER_IMPACT_WEIGHT`
- `MARKET_OPPORTUNITY_COMPETITOR_STRENGTH_WEIGHT`
- `MARKET_OPPORTUNITY_STOCK_READINESS_WEIGHT`
- `MARKET_OPPORTUNITY_PRICE_READINESS_WEIGHT`
- `MARKET_OPPORTUNITY_DATA_CONFIDENCE_WEIGHT`
- `MARKET_OPPORTUNITY_HIGH_THRESHOLD`
- `MARKET_OPPORTUNITY_MEDIUM_THRESHOLD`
- `MARKET_OPPORTUNITY_WINDOW_DAYS`
- `MARKET_OPPORTUNITY_FORMULA_VERSION`

## Revenue Estimation Limitations

Revenue estimates require historical sales volume. When baseline sales are unavailable, `estimated_revenue` is `null` and the frontend displays `Insufficient sales history`. The dashboard must not substitute `৳0` or `BDT 0` for missing estimates.

The current implementation records the evidence and confidence penalty so later sales-history integration can produce estimates without changing the opportunity contract.

## Celery Workflow

Task:

- `phase5.run_analysis_workflow(scrape_run_id)`

The task:

- only processes `COMPLETED` scrape runs
- uses a PostgreSQL advisory lock when available
- relies on database uniqueness for idempotency
- generates events before rankings
- generates opportunities after rankings
- publishes dashboard notifications after database commits

Standalone tasks exist for targeted replay:

- `competitor_events.generate_for_scrape_run`
- `competitor_rankings.calculate_for_scrape_run`
- `market_opportunities.generate_for_scrape_run`

## Redis and Socket.IO

Phase 5 reuses the existing Socket.IO emitter and Redis-backed deployment path.

Published event names:

- `competitor.snapshot.created`
- `competitor.event.created`
- `competitor.rankings.updated`
- `market.opportunity.created`
- `competitor.summary.updated`

Envelope:

```json
{
  "version": 1,
  "event": "competitor.event.created",
  "seller_id": "seller-id",
  "product_id": "product-id",
  "occurred_at": "2026-06-29T12:00:00Z",
  "data": {}
}
```

Rooms:

- `seller:{seller_id}`
- `product:{product_id}`

Clients must authenticate before joining rooms. Product-room joins are authorized server-side against seller ownership.

Publication happens after database commits. If Redis or Socket.IO publication fails, database records remain durable and clients recover by refetching APIs.

## Backfill Command

Run snapshot backfill after deploying the migrations if historical competitor rows need snapshots:

```bash
cd backend
venv/bin/python scripts/backfill_competitor_snapshots.py
```

Backfilled snapshots establish history for future comparisons. They do not automatically replay all Phase 5 analysis unless Celery tasks are triggered for the relevant completed runs.

## Production Deployment Procedure

1. Deploy database migrations.
2. Deploy backend API and Celery workers from the same release.
3. Confirm Redis broker and Socket.IO configuration.
4. Start workers and scheduler.
5. Deploy frontend.
6. Run a controlled scrape for one seller-owned product.
7. Verify snapshots, events, rankings, opportunities, dashboard APIs, and Socket.IO invalidation.

## Known Limitations

- Revenue estimation is conservative until historical sales data is available.
- Socket publication is not a transactional outbox. The database is the recovery source if publication fails.
- The dashboard refetches after Socket.IO events instead of mutating complex feed caches.
- Advisory locks require PostgreSQL. In non-PostgreSQL test environments the workflow falls back to database idempotency.
- Existing frontend build emits CSS minifier warnings for third-party shadcn/Tailwind at-rules.
